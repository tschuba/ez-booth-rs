# Register-to-Register Sync & Reconciliation Trust — Planning Document

Prepared on 2026-06-25 to capture the design direction agreed for multi-register reconciliation, ahead of formal OpenSpec proposals. This is a living document — update it as decisions firm up, and draw proposals from it incrementally rather than all at once.

## Context

This started as an open exploration of how to make `ez-booth-rs` more self-service — the goal being to reduce how often the project owner (or any trainer) has to physically stand next to friends running an event. Working through the full event lifecycle (onboarding, operating, troubleshooting, offboarding) surfaced many smaller findings (tone consistency, missing `navigator.storage.persist()`, dormant storage-warning proposal, docs aimed at developers not organisers, etc.) — but one fact reframed everything: **running two simultaneous checkout registers ("Kassen-App" stations) is the default, required operating mode**, not an edge case, since one register can't handle buyer volume alone.

Today, each register is a fully independent IndexedDB with zero connection to the other. The only reconciliation path is a manual, end-of-event procedure (`docs/user-guides/MULTI_DEVICE_MERGE_GUIDE.md`): export a backup from each device, pick one as "the merge device," import the other with `Merge`, then manually eyeball a checklist (vendor count, purchase count, totals) to convince yourself nothing was lost or double-counted. This is risky in a way that matters because the merged number directly determines **vendor payout**:

- Devices/participants aren't reliably available at end-of-event to gather for the merge — volunteers leave early, borrow phones, may never reopen the app again. The model assumes universal presence at closing; that assumption doesn't hold.
- There's no way to know, short of exporting and comparing files by hand, whether two registers are currently in sync, already merged, or merged more than once.
- Venue WiFi commonly has client/AP isolation, which is why local-network discovery approaches were already rejected in `docs/technical/ADR_DEVICE_TO_DEVICE_TRANSFER.md` — but both devices can usually still reach the open internet through the same router even when they can't reach each other.
- This is institutionally sensitive: the original Java predecessor app's opaque background persistence jobs caused users to distrust whether checkouts had even saved — that exact transparency failure is what drove this Rust rewrite. An untrackable cross-device merge state is the same failure shape, recurring at a different layer.

Two OpenSpec changes are already in flight that look adjacent but **do not cover this gap**, confirmed by reading both specs directly:

- `ez-booth-server` — builds the optional server (axum/sqlx), with `POST /api/sync` and `GET /api/sync?since=` already specced generically (not phone-specific).
- `qr-labels-webcam-mobile-sync` — has the Mobile-App (phone scanning helper) **POST** to that endpoint, and the Kassen-App only ever **GET**s. The Kassen-App never POSTs its own directly-entered sales. Even fully built, two registers running plain checkout (no mobile scanning involved) still would not sync with each other — line 451 of that design doc acknowledges multi-register setups exist, but its only mitigation is a manual "agree on the same event name beforehand" coordination step, not actual data sync.

The owner's non-negotiable constraint: the offline-only, zero-config default must stay exactly as lightweight and simple as it is today. Any sync capability must be strictly optional and invisible when not configured.

## Recommended Direction

**Keep OpenSpec changes small and independently completable.** Every change currently in flight in this repo sits at 0 completed tasks — `ez-booth-server` (0/38), `qr-labels-webcam-mobile-sync` (0/79), `browser-storage-warning-dialog` (0/36), `page-header-actions-context` (0/12), even the small `archived-booth-permanent-delete-token` (0/8). Size alone doesn't explain that pattern, but bundling unrelated-scope work into one change does make partial progress harder to ship and easier to abandon. So rather than one change with two internal phases, this is **two separate, dedicated OpenSpec changes**, not subordinate to either existing in-flight change:

- **Change A — "local reconciliation provenance"**: zero dependency on anything else in flight, small, shippable on its own, immediately.
- **Change B — "register-to-register background sync"**: the larger lift, explicitly depends on `ez-booth-server` existing. Proposed and scheduled separately so it never blocks Change A's release.

### Change A — local reconciliation provenance (ship first, no dependencies)

Today, `device_info` (identifier/platform/browser) and `created_at` already travel inside every exported `BackupData`/`BoothBackupData` (`crates/storage/src/export/backup_format.rs`), but this provenance is discarded after import instead of retained. Add a small local history — one record per import, holding `device_id`, the word-based label, `device_info`, `created_at`, and `purchase_count` (each rationale elaborated below) — so the app can answer, purely offline: *"what has this register already absorbed, and from where"* — directly serving the trust gap without touching the server architecture at all.

**`device_info.identifier` is not safe to use as that history's identity key as-is — verified, not hypothetical.** `generate_default_device_identifier()` (`crates/ez-booth-ui/src/utils.rs:343`) builds the default purely from `{platform}-{browser}` (e.g. "macOS-Safari") with zero random entropy. Two different iPads both on Safari, or two Windows laptops both on Chrome — an ordinary pairing for "friends bring their own device" — silently produce the identical default identifier unless someone manually visits Settings and renames one, which an untrained volunteer won't reliably do. Relying on this string as a provenance key risks Change A's whole "what has this register absorbed, and from where" view silently conflating two genuinely different devices.

**Fix as part of Change A**: introduce a separate, randomly-generated, stable `device_id` (UUID v4) — a *new* `localStorage` key, distinct from the existing human-editable `ez-booth-device-identifier` key so it never collides with or overwrites that display name. Generated once, persisted, never user-edited; this becomes the real identity key for the local history.

Browser-API device fingerprinting (hardware/canvas signals) was considered, to make the identifier more human-guessable, and rejected — those techniques are the same ones associated with tracking/fingerprinting, are actively destabilized by Safari/Firefox privacy hardening, and sit awkwardly against an app whose whole posture in this plan is "nothing happens invisibly to the user." Instead, get human-guessability from a value already being generated: improve `generate_default_device_identifier()`'s default (currently bare `{platform}-{browser}`, e.g. "macOS-Safari", with zero entropy) by appending a short suffix derived from the new `device_id` itself. Prefer a **word-based suffix over a hex one** — e.g. "macOS-Safari-silver-fox" rather than "macOS-Safari-a3f2" — generated by mapping chunks of the `device_id`'s random bits onto a small embedded adjective/noun wordlist (the same idea Docker container names and `petname`-style tools use), no new runtime dependency or server-side registry required. A human can still recognize the prefix ("that's probably my iPad") and now also has something pronounceable and memorable to refer to it by in conversation ("is that the silver-fox one or the quiet-river one?"), while the actual uniqueness guarantee still comes from `device_id` itself — a word-pair collision between two real devices would be cosmetically confusing at worst, never a correctness problem, since `device_id` alone is what the local history and Change B's sync both key on. `device_info`'s fields remain a cosmetic, human-readable label — now genuinely useful — never relied on for correctness or uniqueness.

**Also surface this label more prominently in the UI, while staying subtle**: add it to the existing `StorageIndicator` footer — small, muted text, always visible, not a banner or anything competing for attention — so a person looking at two registers side-by-side always has an ambient answer to "which device is this" without hunting through Settings. This is pure local UI, no server required, so it's in scope for Change A. It also sets up a clean handoff to Change B, which later adds its sync-health line to the *same* footer component alongside this label, rather than each change inventing its own display surface.

### Change B — register-to-register background sync (depends on `ez-booth-server`)

This change needs the server itself running and the `event_code`/`client_id` *wire-protocol conventions* `qr-labels-webcam-mobile-sync` already defines (i.e. the shape of those fields in `/api/sync` requests) — it does not require that change's QR/webcam-scanning features to be built or shipped, only that those conventions exist to be reused. The actual *value* populating `client_id` is Change A's `device_id` (see below) — Change B reuses the protocol shape, not a second generated UUID.

- Kassen-App becomes a sync peer: it POSTs its own locally-entered purchases (not just GETs mobile-sourced ones), reusing the existing `/api/sync` *wire format* verbatim — no payload-shape change needed, since the dedup index already keys on purchase UUID regardless of source. (The auth contract does change — see below.) For the `client_id` this requires, **reuse Change A's `device_id` rather than minting a second, separate identifier** — both changes need exactly the same property (a stable, unique-by-construction per-device UUID), so collapsing them into one avoids ending up with two parallel device-identity concepts that could drift out of sync with each other.
- Reuse the existing `event_code` as the cross-register identity (don't invent a second identifier). Extend its lock trigger from "mobile onboarding QR shown" to "first successful sync of any kind," so organisers who use two registers but never touch mobile scanning still get a coordinated `event_code`.
- The sync-status display lives in the **existing `StorageIndicator` footer** (already present on every Kassen-App page, already the trusted home for storage/backup health) — not a new standalone component. It gains a parallel sync-health line using the same plain-language convention the Mobile-App's batch-status line already established ("N ausstehend · zuletzt synchronisiert HH:MM" / "Alles synchronisiert ✓"), plus a provenance disclosure showing per-register contributed counts. **That disclosure must label each register using Change A's word-based device label (e.g. "silver-fox: 42 Käufe"), never a raw `device_id`/`client_id` UUID** — otherwise this surface quietly reintroduces the unreadable-identifier problem Change A exists to fix. Wording must stay conservative ("Alle Registers synchronisiert ✓ · Letzte Prüfung HH:MM") — never imply cryptographic certainty, since the server provides no protection against fabricated data (already an acknowledged threat model in the mobile-sync design: "organisers must cross-check before payout"). The point is to make that cross-check *fast*, not to claim it's unnecessary.
- **Sync model: automatic, batched, interval-based, bidirectional — eventual consistency by design, not manual-button-only.** This is a direct revision from an earlier draft of this plan, made after explicit owner feedback: the goal is a transparent background sync (up and down) per device so all devices and the server converge on consistent state, with delay and intermediate inconsistency accepted and known as an architectural property rather than something to avoid. This is not a new ambition — `docs/redesign/03_IMPROVEMENTS.md` §6 already named this as the original target when the Rust rewrite was first scoped ("Automatic Sync: Background synchronization when connected... CRDT-Based... start with Option C [simple last-write-wins], migrate to CRDT if conflicts common"). The already-specced `ez-booth-server` mechanics — UUID-keyed dedup, newer-`updated_at`-wins, unconditionally-additive purchases/vendors — already are that Option C starting point; this change is what turns it into an always-on process instead of a one-off contract.
  - Reconciling this with the institutional trust concern (legacy app's opaque background persistence): the failure there wasn't "runs in the background," it was "runs in the background **and gives no visibility into whether it worked.**" The fix is not avoiding backgrounding — it's making eventual-consistency state always visible. Extend the existing `StorageIndicator` footer pattern (persistent green/amber traffic light, already used for backup freshness) with a parallel sync-health signal: last-successful-sync timestamp and pending-count, visible continuously on both registers, not just after a manual action.
  - At the one moment it actually matters financially — archiving/payout, via `ArchiveWizard` — force a final blocking sync-to-completion pass before the wizard proceeds, converting "eventually consistent" into "confirmed consistent right now" exactly when the number gets locked in for vendor payout.
  - Keep a manual "sync now" override available (for impatience or troubleshooting), but it's a secondary affordance, not the primary mechanism.
- This forces resolution of a currently-deferred decision in `ez-booth-server`'s proposal: single-tenant `/api/sync` auth. Recommendation — once registers are financially-authoritative peers (not just a one-way "any phone can post"), default single-tenant `/api/sync` to require an API key with Cashier role. This *is* a contract change (adding an auth requirement where none existed), distinct from the payload-shape reuse above.

### Explicit non-goals

Shared by both changes:

- Does not remove or deprecate the manual export/import/merge workflow — it stays the permanent zero-server fallback, for organisers who configure no server at all.
- No browser fingerprinting APIs (canvas/WebGL rendering signals, hardware concurrency, device memory, etc.) for device identification — considered and explicitly rejected during design; see Change A's `device_id` rationale for why (privacy exposure, instability under browser privacy hardening, conflicts with the app's transparency posture).

Specific to Change B (sync) — Change A has no transport, totals, or conflict-resolution surface, so none of these apply to it:

- No real-time/live combined totals across registers — confirmed not needed.
- No automatic conflict *interpretation* (guessing two purchases are "the same real-world sale") — already explicitly out of scope per the existing merge guide.
- No new transport mechanisms (no local WiFi server, Bluetooth, WebRTC) — rides the same internet-reachable `/api/sync` path mobile already uses, deliberately avoiding any local-network discovery given the AP-isolation finding.

## Architectural Constraint: Modular, Extensible Server (cross-cutting, bigger than this change)

The owner's vision for `ez-booth-server` extends beyond this one capability: a modular, extensible architecture where individual components/features can be enabled or disabled per deployment — supporting different hosting tiers and leaving room for future commercialization (free self-hosted core vs. paid/licensed modules and/or paid managed hosting). `ez-booth-server`'s own proposal already names this business-model dimension ("free self-hosted vs. paid managed instances") and already has one compile-time lever (`--features multi-tenant`), but the owner is now asking for something more granular:

- Feature enablement via **Docker Compose profiles**, or by toggling which server components run, not only compile-time feature flags — deploy-time granularity, so enabling a feature can be "deploy a different compose profile" rather than "recompile the binary."
- A **routing proxy** in front of these components, directing requests to whichever are actually enabled for a given deployment.
- **Sync is core, not a paid module** — register-to-register sync and all related components (the subject of this plan) must ship in the free/base tier on every deployment, never gated behind licensing. This plan's sync capability should therefore be scoped and built as a discrete "core sync module" that slots cleanly into whatever modular boundary `ez-booth-server` adopts — not entangled with any future paid add-on's code or deployment unit.
- **Reference deployment target**: `ez-booth-server` on Coolify, hosted on a Raspberry Pi, exposed via a `*.schubs.net` subdomain. This reinforces `ez-booth-server`'s existing SQLite-default, single-binary, low-footprint choices — any modular/proxy design must stay comfortable on Raspberry-Pi-class hardware (including ARM Docker image builds), not assume cloud-scale resources.

This modularity/licensing boundary is foundational to `ez-booth-server` as a whole — every future module and any commercialization model depends on getting it right once — so it should be raised as an **amendment to `ez-booth-server`'s own proposal/design**, not absorbed into Change A or Change B. This plan's responsibility is narrower: ensure Change B is designed to slot in as the always-on core sync module once that boundary exists, and flag the amendment as a recommended parallel action (see Status & Next Steps).

The same small-changes principle from "Recommended Direction" applies here too: `ez-booth-server`'s current proposal already bundles four capabilities (`sync-api`, `server-auth`, `api-key-management`, `tenant-provisioning`) into one change. Splitting those into separate proposals — likely a `server-core` foundation (axum skeleton, DB connection, health check, Docker base image, the Compose-profile/proxy composition mechanism) that `server-auth`+`api-key-management` (kept together; they share the `AuthContext` middleware) and `tenant-provisioning` each depend on independently — is worth doing for the same reason: smaller, independently shippable pieces instead of one 38-task change sitting at 0% complete. That split should happen as part of the amendment above, sequenced *before* any further capability is speced against it, so new proposals (including Change B) land on settled seams rather than ones likely to move.

## Key Files

- `openspec/changes/ez-booth-server/specs/sync-api/spec.md` — existing wire contract being reused; needs one amendment (Cashier-role auth default for single-tenant).
- `openspec/changes/qr-labels-webcam-mobile-sync/design.md` (§9–§13) — existing `client_id`/`event_code`/sync-status-UI patterns being extended to the Kassen-App.
- `crates/storage/src/export/backup_format.rs` — existing `device_info`/`created_at` provenance fields; currently read only transiently (e.g. for export filename generation) and never retained or surfaced after import. Change A retains and surfaces them, alongside the new `device_id`.
- `crates/ez-booth-ui/src/utils.rs` — existing `generate_default_device_identifier()`/`load_or_create_device_identifier()` (non-unique default identifier, verified) and the existing `ez-booth-device-identifier` `localStorage` key; Change A adds the new, separate `device_id` key here, plus a small embedded adjective/noun wordlist for the word-based suffix, without touching the existing display-name logic.
- `crates/storage/src/export/import_service.rs` — existing `ConflictStrategy`/`BoothResolution` logic; Change A's local history hooks in here at import time.
- `docs/user-guides/MULTI_DEVICE_MERGE_GUIDE.md` — the manual fallback this design must not break.
- `crates/ez-booth-ui/src/components/storage_warning.rs` (`StorageIndicator`) — the existing footer status component. Change A adds the subtle, always-visible device label here; Change B later adds its sync-health line to the same footer, rather than either change introducing a separate widget.
- `crates/ez-booth-ui/src/components/archive_wizard.rs` (`ArchiveWizard`) — gains the forced final sync-to-completion step before archiving/payout (Change B).

None of them block or are blocked by Change A or Change B.

### Verification

Since proposing work from this document produces OpenSpec proposals, not application code, "verification" means: run `openspec validate <change-name> --strict` after each proposal is generated, and confirm each one's stated dependencies are accurate — Change A declares none; Change B declares `ez-booth-server` (existence, not full implementation) and the `event_code`/`client_id` conventions from `qr-labels-webcam-mobile-sync` — so `openspec list` reflects the real ordering instead of gating Change A on anything.
